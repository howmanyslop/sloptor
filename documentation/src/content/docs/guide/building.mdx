`sloptor build` compiles every file in the project, writes the `.luau` outputs to your tsconfig's `outDir` exactly where `rbxtsc` would put them, runs the cleanup/copy pipeline, emits `.d.ts` files when `compilerOptions.declaration` is enabled, and copies `include/` (RuntimeLib.lua, Promise.lua — verbatim from roblox-ts). Try it on the test fixture project in the sloptor repository:

```powershell
bun install --cwd testdata/diff/project --no-save
sloptor build testdata/diff/project
# out/01_literals.luau
# ...
# compiled 43 files in 189 ms
```

A standalone `.ts` file isn't compilable by itself — like `rbxtsc`, sloptor needs the rbxts project around it (`package.json` with `@rbxts/compiler-types` + `@rbxts/types` installed, `tsconfig.json`, `default.project.json`). The fixture project above is a minimal working example of that setup.

`sloptor build` accepts the rbxtsc-compatible flag surface (booleans accept `--flag`, `--flag=false`, `--no-flag`): `-p/--project`, `-b/--build [path]`, `--builders <n>`, `--checkers <n>`, `--singleThreaded`, `--emitDeclarationOnly`, `-w/--watch`, `--usePolling`, `--verbose`, `--noInclude`, `--logTruthyChanges`, `--writeOnlyChanged`, `--writeTransformedFiles` (parsed and ignored), `--optimizedLoops`, `--type game|model|package`, `-i/--includePath`, `--rojo`, `--allowCommentDirectives`, and `--luau`. sloptor adds `--optimizedArrayAppends`, `--luauTypes` (experimental), `--cpuprofile`, `--trace-out`, `--blockprofile`, `--mutexprofile`, `--heapprofile`, `--timings`, `--max-errors`, `--json`, `--bell`, and `--no-clear`. `--optimizedArrayAppends` replaces eligible built-in `Array.push` calls in loops over fresh local arrays with loop-carried indexed writes and defaults to off. `--builders` requires `--build`. `--singleThreaded` is the tsgo flag of the same name: when effective it forces one solution builder and one checker per program, even if `--builders`/`--checkers` are larger. There is no `--parallel` flag. `--emitDeclarationOnly` requires `--build`; `--build --watch` cannot be combined with declaration-only emit. The finite profiling and timing flags cannot be combined with `--watch`. Run `sloptor build --help` for the rendered descriptions.

TypeScript build integrations may use the compiler-shaped `sloptor --build [path]` (or `sloptor -b [path]`) invocation. These are compatibility aliases for `sloptor build --build [path]`; the `build` subcommand remains the normal CLI surface.

Options may also be set under the top-level `"rbxts"` key of `tsconfig.json`; merge order: defaults < rbxts < command line.

**sloptor DX extensions** (not in rbxtsc; safe to ignore for parity):

- **`--minify`** — pass every emitted `.luau`/`.lua` source through the Luau minifier (comment/whitespace stripping + `t["x"]` → `t.x`) before writing. It is opt-in; declaration and `include/` files are never minified.
- **Code-frame diagnostics** — TypeScript, transformer, and macro errors render as grouped code frames (source line + caret/underline, keyword highlighting, OSC 8 file links, an `✗ N errors in M files` footer). `--max-errors <n>` caps the rendered frames (default 50; `0` = all). In watch mode the screen clears before each rebuild (opt out with `--no-clear`), a `✗ N errors` banner persists on the idle line until the next green build, and `--bell` rings the terminal on a fail↔pass transition.
- **`--json`** — emit one machine-readable result object (version, ok, files, durationMs, diagnostics with `file`/`line`/`col`/`code`/`severity`/`message`) instead of styled output. `file` is relative to the project directory (the solution tsconfig directory with `--build`). `code` is `TS####` for a TypeScript diagnostic and the upstream factory name for a transformer one, and is omitted when the diagnostic has none. Also available on `sloptor check`.
  With `-w/--watch`, stdout is an NDJSON stream (one object per line, no styled output) for tools that supervise the watcher. Each build (the initial one too) prints a `buildStart` event (`at`, `changed` paths relative to the project) and then exactly one `buildEnd` event (`at` plus the one-shot result fields). Pairs never nest, so "build in progress" is a toggle. The first event carries `version`, and one `watching` event (`at`, `files`: the watched file count) follows the initial `buildEnd`. Compiler warnings go to stderr. Works with `--build --watch` too.

    ```jsonc
    {"event":"buildStart","at":"2026-09-25T17:59:59.000Z","version":"2.7.1","changed":[]}
    {"event":"buildEnd","at":"2026-09-25T17:59:59.300Z","version":"2.7.1","ok":true,"files":222,"durationMs":300,"diagnostics":[]}
    {"event":"watching","at":"2026-09-25T17:59:59.310Z","files":240}
    {"event":"buildStart","at":"2026-09-25T18:00:00.000Z","changed":["src/a.ts"]}
    {"event":"buildEnd","at":"2026-09-25T18:00:00.142Z","version":"2.7.1","ok":false,"files":0,"durationMs":142,"diagnostics":[{"file":"src/a.ts","line":3,"col":7,"code":"TS2322","severity":"error","message":"..."}]}
    ```

- **One-shot diagnostics** — `--cpuprofile`, `--trace-out`, `--blockprofile`, `--mutexprofile`, `--heapprofile`, and `--timings` can be combined on one build. sloptor finalizes requested profiles even when the build fails, which keeps failed-build traces usable. `--timings` writes schema version 2: `totalMs` is elapsed wall time for the whole command (including deferred solution persistence, excluding profile serialization); `stages` are aggregate work milliseconds and may exceed `totalMs` when projects overlap. Solution builds also emit `projects[]` in graph order. Go CPU/block/mutex/heap profiles cover the parent process only — they do not include Node transformer-sidecar CPU or heap. Profile flush can add CLI wall time after the timing JSON is closed; `--verbose` prints a `finalize profiles` stage for that tail.

## Native code generation annotations

This is an opt-in rotor extension and off by default. Enable it in either project file — `tsconfig.json`:

```json
{
	"rbxts": { "nativeTypes": true }
}
```

or `rotor.toml`:

```toml
nativeTypes = true
```

`rbxts.nativeTypes` wins when both are set; `rotor.toml`'s value applies only when the tsconfig does not declare the key. With the option off, a `//!native` file compiles exactly like rbxtsc: the directive comment is still emitted as `--!native`, but no annotations, type aliases, or generic declarations are added.

With it on, a file whose leading comments include `//!native` gets Luau type annotations on its function parameters and return types, which is what Luau's native compiler specializes on. sloptor emits the directive as `--!native` and annotates every function in the file. Files without the directive produce the same Luau as rbxtsc.

```ts
//!native
export function scale(x: number, factor = 2, label?: string): number {
	return x * factor;
}
```

```lua
--!native
local function scale(x: number, factor: number?, label: string?): number
```

Annotations follow the TypeScript type:

| TypeScript type                                                        | Emitted                         |
| ---------------------------------------------------------------------- | ------------------------------- |
| `number`, numeric literals and enums, generics constrained to `number` | `number`                        |
| `string`, template literals like `a${string}`                          | `string`                        |
| `"there"`, `"a" \| "b"`                                                | `"there"`, `"a" \| "b"`         |
| `true`, `false`                                                        | `true`, `false`                 |
| `true \| false` (the whole boolean)                                    | `boolean`, or `boolean?`        |
| `vector`, `Vector3`                                                    | `vector`, `Vector3`             |
| `T[]`, `ReadonlyArray<T>`, `[A, B]`                                    | `{ T }`, `{ A \| B }`           |
| `Map<K, V>`, `Set<K>`, `Record<K, V>`, index signatures                | `{ [K]: V }`, `{ [K]: true }`   |
| named interfaces and non-generic object type aliases                   | a `type` alias (where declared) |
| anonymous object types                                                 | `{ a: number, b: string? }`     |
| function types                                                         | `(key: K, other: T?) -> V`      |
| a `LuaTuple<[A, B]>` return                                            | `(A, B)`, a return pack         |
| `new (x: number) => T`, `typeof Class`                                 | `{ new: (x: number) -> T }`     |
| a generic call signature                                               | `<T>(value: T) -> T`            |
| several call signatures                                                | `((A) -> B) & ((C) -> D)`       |
| a `void` return                                                        | `()`, so a function gets `: ()` |
| a shape that cannot be written out                                     | `{ [any]: any }`, or none       |
| anything else                                                          | none                            |

A named interface — and a non-generic `type X = { ... }` alias — is emitted once as a Luau type alias, and every reference uses it, so a recursive type stays recursive instead of collapsing to `{ [any]: any }`. A declaration that is a top-level statement of the compiled file emits its alias at the declaration, after that declaration's leading comments, so the alias reads next to the TypeScript it describes. Luau resolves an alias declared later in the same block, so a use that appears above the declaration still works. A merged interface (`interface Hi { ... }` declared several times) emits one alias, at its first declaration, with every merged member.

```lua
type Node<K, V> = { key: K, nextNode: Node<K, V>?, value: V }
```

Anything that is not a top-level declaration of this file — an interface or alias inside a namespace, function, or block, a type imported from another module, or an ambient/library type — is hoisted next to the header instead, where it cannot fall out of scope. The name-collision suffix (`Node_2`) is the same in either position.

`readonly` is dropped because `read` is illegal inside a Luau table type; optional members are spelled `T?`. A function's own type parameters are declared and used by name (`local function f<K, V>(callback: (key: K) -> V): (key: K) -> V`). Constraints are dropped, because Luau has no `extends` clause, and a class type parameter maps to `any` — Luau cannot declare one.

Table shapes are followed into nested members, so `Map<string, number[]>` becomes `{ [string]: { number } }`; names that are not Luau identifiers are quoted (`["kebab-case"]: number`), and a shape that recurses or nests past four levels falls back to `{ [any]: any }`. Nested positions — alias bodies, members, elements, keys and values, and function parameters and returns — mirror in full: `boolean`, string and boolean literals (`there: "there"`, `flag: false`; `true | false` is just `boolean`, and `true | false | undefined` is `boolean?`), function types, and Roblox types by name from a fixed allowlist (`CFrame`, `Color3`, `TweenInfo`, `Vector3`, …) plus interfaces that extend `Instance`.

Callable shapes are spelled in full too. A function returning `LuaTuple<[A, B]>` gets the return pack `: (A, B)`, and the same pack appears inside a callback type (`cb: () -> (number, string)`); `[A, B?]` becomes `(A, B?)`, `[A, ...C[]]` becomes `(A, ...C)`, and an empty tuple becomes `()`. A `LuaTuple` whose argument is not one fixed tuple — a plain array, a generic, a union of tuples — keeps the parameters and loses the pack: `() -> ...any` in a function type, and no annotation at all on a declared function, because `?` after a pack would mean "optional function" rather than an optional return. Outside a return position a `LuaTuple` is `any`: a pack is not a type, so it is never aliased. A construct signature (`new (x: number) => T`, or `typeof SomeClass`) is the table roblox-ts emits at runtime, `{ new: (x: number) -> T }` followed by the class's statics, with the instance widened to `any` when it cannot be spelled. A generic call signature keeps its parameters (`<T>(value: T) -> T`), and several call signatures become an intersection, `((A) -> B) & ((C) -> D)` — everywhere except a tagged top-level parameter, where an intersection is not tagged at all and `(...any) -> ...any` keeps the `function` tag.

Top-level parameters are what Luau actually tags, so their policy is narrower. Only `number`, `string` (a single string literal or a union of them too — Luau's compiler tags both as `string`), `vector`/`Vector3`, table types, function types, and the function's own generics are annotated. `boolean` and boolean literals, Roblox datatypes and `Instance`s, class instances, unions that mix a table with a non-table, and a bare generic from an enclosing function stay unannotated. The last one matters: Luau only tags a bare generic name as `any` when the annotated function declares that generic. An outer function's generic is tagged userdata, so the native entry guard would fail on every call.

A parameter that callers may omit becomes optional: a `?` marker, a default value, or `undefined` in the type all emit `T?` and cost one extra nil check in native code. `self`, `this`, rest, and destructured parameters stay unannotated, as do async functions and generators. An overloaded callable passed as a parameter keeps the `(...any) -> ...any` fallback, so the argument still gets an entry guard.

sloptor never emits a bare `table`. Luau's compiler tags it as userdata, so the native entry guard would fail on every call.

Return annotations don't affect native code generation. They only help Luau's type checker. A wrong annotation costs an interpreter fallback, never a crash. Luau's analyzer may still warn that a defaulted parameter is `number?` where the body uses it in arithmetic after the `if x == nil then x = default end` check. That only affects Studio script-analysis warnings, and the `?` is required: an omitted argument arrives as `nil`, and a plain `number` annotation would send every such call back to the interpreter.

## Luau type annotations (experimental)

`luauTypes` is an experimental, opt-in rotor extension and off by default. With the option on, sloptor emits full Luau type annotations in every compiled file. That covers parameters, `...`, returns, generics, the `self` of every method, locals that Luau can't infer, class instance aliases, enum aliases, and a `type` / `export type` statement for every interface and type alias. Luau code that requires the output then gets real types instead of `any`. The emitted Luau differs from rbxtsc, and the output may change between releases. The design record is `docs/superpowers/specs/2026-10-29-luau-types-design.md`.

Enable it on the command line, in `tsconfig.json`, or in `rotor.toml`:

```sh
sloptor build --luauTypes
```

```json
{
	"rbxts": { "luauTypes": true }
}
```

```toml
luauTypes = true
```

The command-line flag overrides both files, and `--luauTypes=false` turns a declared option off again. `rbxts.luauTypes` overrides `rotor.toml`, whose value applies only when neither of the others declares the key. Toggling the option changes the incremental salt, and the next build rewrites every output. With `nativeTypes` also on, a `//!native` file keeps the native policy for its signatures: parameters, returns, generics, and the colon-form class methods that come with them. `luauTypes` still annotates that file's locals, enums, and type aliases. The option doesn't depend on a comment directive, and `removeComments` leaves it on.

### Before and after

A module with an interface, a string enum, a function with a defaulted parameter, and a class:

```ts
export interface Point {
	x: number;
	y: number;
}

export enum Direction {
	Up = "up",
	Down = "down",
}

export function scale(point: Point, factor = 2): Point {
	return { x: point.x * factor, y: point.y * factor };
}

export class Counter {
	constructor(public count: number) {}

	step(direction: Direction): number {
		this.count += direction === Direction.Up ? 1 : -1;
		return this.count;
	}
}
```

With the option off it compiles to the same Luau as rbxtsc:

```lua
local Direction = {
	Up = "up",
	Down = "down",
}
local function scale(point, factor)
	if factor == nil then
		factor = 2
	end
	return {
		x = point.x * factor,
		y = point.y * factor,
	}
end
local Counter
do
	Counter = setmetatable({}, {
		__tostring = function()
			return "Counter"
		end,
	})
	Counter.__index = Counter
	function Counter.new(...)
		local self = setmetatable({}, Counter)
		return self:constructor(...) or self
	end
	function Counter:constructor(count)
		self.count = count
	end
	function Counter:step(direction)
		self.count += if direction == Direction.Up then 1 else -1
		return self.count
	end
end
return {
	scale = scale,
	Direction = Direction,
	Counter = Counter,
}
```

With `luauTypes` on:

```lua
export type Point = { x: number, y: number }
export type Direction = "up" | "down"
local Direction: { read Up: "up", read Down: "down" } = {
	Up = "up",
	Down = "down",
}
local function scale(point: Point, factor: number?): Point
	if factor == nil then
		factor = 2
	end
	local factor = factor :: number
	return {
		x = point.x * factor,
		y = point.y * factor,
	}
end
export type Counter = { count: number, step: (self: Counter, direction: Direction) -> number }
local Counter = setmetatable({}, {
	__tostring = function()
		return "Counter"
	end,
})
do
	Counter.__index = Counter
	function Counter.new(count: number): Counter
		local self = (setmetatable({}, Counter) :: any) :: Counter
		return Counter.constructor(self, count) or self
	end
	function Counter.constructor(self: Counter, count: number)
		self.count = count
	end
	function Counter.step(self: Counter, direction: Direction): number
		self.count += if direction == Direction.Up then 1 else -1
		return self.count
	end
end
return {
	scale = scale,
	Direction = Direction,
	Counter = Counter,
}
```

A Luau consumer of the compiled module gets `Point`, `Direction` and `Counter` as importable types: `local M = require(path)`, then `M.Point`. It also gets a checked `M.scale(p, 3)`, a `Counter.new(1)` whose result has `count` and `step`, and an error on `M.scale("x")` or `Direction.Sideways`.

What changed, line by line:

- Every interface and type alias of the file becomes `type` / `export type` at its declaration. `readonly` is `read`, optional members are `T?`, `T[]` is `{ T }`, `Map`/`Set` are `{ [K]: V }` / `{ [K]: true }`, overloads are `((A) -> B) & ((C) -> D)`, and `keyof T` / `T[K]` with an unresolved `T` are `keyof<T>` / `index<T, K>`. sloptor mirrors types from a namespace, a function, another file, `node_modules` or the lib as hoisted aliases after the header, under their local import name, because `TS.import` is opaque to Luau's checker. A name that collides with a Luau builtin, a Roblox type, or a type parameter used in the file takes `_2`.
- Parameters and returns take the TypeScript type: `?` and a default make `number?`, a rest parameter annotates `...: string`, a destructured parameter annotates its `_param` temp, and `this` is `self`. A `LuaTuple<[A, B]>` return is the pack `(A, B)`, `void` is `()`, and a void body with an explicit `return` is `...nil`. Neither Luau solver refines `factor: number?` through the `if factor == nil then` default, and the shadow `local factor = factor :: number` after it supplies the narrowing instead. A `??`, `||` or `&&` temp gets the same re-binding.
- Locals get an annotation only where Luau can't infer them. That covers a local with a written type or no initializer, an imported binding, and a value coming out of the `RuntimeLib`: `TS.import`, `TS.async`, `TS.await`. An `async` function's local gets the type `(n: number) -> Promise<number>`, while the callback inside `TS.async` returns the settled type.
- A class becomes a structural instance alias and a class table initialized on its declaration line. The alias leaves `constructor` out and re-lists inherited members, with an explicit `self` on every method. `new` takes the constructor's parameters and builds `self` through `(setmetatable({}, Counter) :: any) :: Counter`, then calls `Counter.constructor(self, ...) or self`. Every method is a dot-form function with an annotated `self`. Class generics appear again on every function, for example `function Box.get<T>(self: Box<T>): T`, and statics take `self: typeof(Counter)`. The colon form never appears: a colon-form `self` is an inferred table unrelated to the alias, and `self.nope` passes without an error.
- A string enum is a union alias plus a `read` map, and a numeric enum is `number` plus the inverse-indexed table. A `const enum` is the alias alone.
- A generic alias whose body is a mapped, conditional or template literal type becomes a Luau `type function`. It computes the same type at analysis time, and `Partial2<T>`, `T extends (infer U)[] ? U : T` and ``{ [K in T as `on${K}`]: () => void }`` all translate this way. `Partial`, `Required`, `Readonly`, `Pick`, `Omit`, `Record`, `Exclude`, `Extract`, `NonNullable`, `ReturnType` and `Parameters` used with a free type parameter go through a hoisted prelude such as `__Partial<T>`. Used with concrete arguments they expand to the exact resolved type.

### Luau's new solver

`keyof<T>`, `index<T, K>` and user-defined `type function`s exist only under Luau's new type solver, and the class idiom relies on its subtyping. That's `luau-analyze`'s default since 0.721, `luau-lsp analyze --flag:LuauSolverV2=true` on the command line or `luau-lsp.fflags.enableNewSolver` in the editor, and the new type solver in Roblox Studio. sloptor doesn't add a mode directive. A `//!strict` comment at the top of the TypeScript file passes through as `--!strict` as before, and sloptor's own tests check the output in strict mode.

### What is lossy

Luau can't say everything TypeScript can. sloptor records each substitution below as a fidelity loss. Only the alias-level ones get a `-- luauTypes: <type> spelled as <Luau>: <reason>` comment before the statement. The full list and policy are in `docs/superpowers/specs/2026-10-29-luau-types-design.md`.

- A tuple used as a value type, `[A, B]`, is `{ A | B }` and loses its positions, because Luau has packs only in parameter and return positions. A rest parameter typed by a tuple or a bare type parameter is `...any`.
- Number literal types such as `1 | 2` and numeric enum members are `number`, because Luau has no number singletons. Template literal types are `string`, `bigint` is `number`, and `symbol` is `any`.
- `LuaTuple<[A, B?]>` is `(A, B?)`. A Luau pack requires every element, which means a short return must pass `undefined` explicitly. `LuaTuple<...> | undefined` is `...any`, and a `LuaTuple` outside a return position is `any`.
- sloptor drops generic constraints, because Luau has no `extends`. On class instances it drops `readonly` and exposes private members, because the constructor writes through `self`.
- sloptor emits a type function only for what the translator can express. An `infer` outside `T extends (infer U)[]` and `T extends (...args: any) => infer R`, an `as` clause, a member type naming another alias such as `Uppercase<K>`, `Box<T[K]>` or `Promise<infer U>`, or a self reference makes the whole alias `any` under a loss comment. Uses of such an alias with concrete arguments still expand exactly. Only generic uses get the `any`.
- A recursive alias referenced with different arguments, such as `Weird<T[]>` inside `Weird<T>` or the lib's `Promise<T>`, spells that member `any`, as Luau's recursion rule requires.
- A class referenced before its declaration keeps the hoisted `local Late: any`. A class value, `typeof Foo`, is the structural `{ new: ..., statics }` table with no `self` on the statics. The new solver can't instantiate a generic method called through a subtype receiver, such as `pair.map(...)` where `Box<T>` declares `map`. Call it through the base type instead.
- `typeof x` stays `typeof(x)` only for a top-level `const`, function or class that the same file declares before the use. Anything else takes its spelling from the resolved type. `export { X as Y }` keeps `X` as the alias name.

## Shell completion

`sloptor completion <bash|zsh|fish|powershell>` writes a native completion
script to stdout — no installation side effects, so redirection works
unchanged:

```sh
sloptor completion bash > /etc/bash_completion.d/sloptor
sloptor completion zsh > "${fpath[1]}/_sloptor"
sloptor completion fish > ~/.config/fish/completions/sloptor.fish
sloptor completion powershell | Out-String | Invoke-Expression
```

The scripts are generated from the live command tree, so they stay in sync
with the flags and subcommands above.

## Tsconfig schema publication

The `rotor.toml` schema and the tsconfig `rbxts` schema are separate documents. `sloptor schema` prints the hosted `rotor.toml` schema; `sloptor schema --rbxts` prints the eight-key tsconfig extension schema. Publish the latter where your project editors can read it:

```sh
sloptor schema --rbxts > rbxts-tsconfig.schema.json
```

Use `"$schema": "./rbxts-tsconfig.schema.json"` in `tsconfig.json`. The `rbxts` values merge through the `extends` chain from parent to child, path values resolve relative to the file that declares them, and command-line values win over tsconfig values. CLI-only values such as `watch`, `verbose`, and `usePolling` are warned about and ignored when placed under `rbxts`.

## Project references, source maps, plugins, and build state

`sloptor build --build` drains project references in dependency order. A coordinator tsconfig with only `references` is not compiled as a project of its own. Each referenced project gets the options its own direct build would: defaults, then its `rbxts` key, then the command line. The entry project's `rbxts` key does not reach its references. A coordinator's `rbxts` key applies to every project, below each project's own key. `type` and `rojo` are the exception: `--type`, `--rojo` and the coordinator's values reach only projects that have no `rbxts` key, and only under a coordinator. `--emitDeclarationOnly` applies to the solution build and cannot be watched. `--build --watch` watches the solution's tsconfig extends chain and Rojo topology, invalidating dependent projects when a referenced project changes.

With `compilerOptions.sourceMap: true`, sloptor writes an adjacent `.luau.map` for each Luau output. The map's `sourcesContent` is the original pre-transformer TypeScript, and source-map files are not counted as emitted Luau files. Declaration maps are kept while their corresponding source exists.

External transformer plugins remain compatible with the fork's `compilerOptions.plugins` shape and run through sloptor's Node sidecar. `before` transformers run before `after` transformers; custom `afterDeclarations` transformers are unsupported, warned about, and skipped. Declaration emit and declaration maps run natively. A plugin's `shouldTransformSourceFile` hook can skip a file, and plugin loading failures are build diagnostics. Builds that resolve external plugins require Node.js and the project's own `typescript` package.

Native `[flamework]` builds do not require Node.js.

On an incremental rebuild sloptor narrows the sidecar's `LanguageService` root set to the files it is recompiling plus every file that can reach them without being imported — declaration files, global scripts, and modules that open `declare global` — instead of handing the worker the whole project. TypeScript pulls each root's import closure into the program, so a transformer that asks the checker about a file it was handed gets the same answers. **A transformer that instead enumerates `program.getSourceFiles()` to build program-wide state sees only the narrowed program on an incremental rebuild, and can go stale.** `rbxts-transformer-jecs`, `rbxts-transformer-jest`, the React-compiler applier and native Flamework are all per-file and unaffected. A full build is never narrowed, so deleting the project's `*.rbxtsc.tsbuildinfo` is the escape hatch for a transformer that needs the whole program.

Successful builds may leave these generated or cached files. They are build state, not source files:

| File or directory      | Purpose                                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `rbxts.copyfiles.json` | `outDir` copy-files gate manifest; lets an unchanged build skip cleanup and copy work                               |

## Incremental rebuild selection

sloptor records a manifest of every source file's content hash, its resolved references, and the content hash of every output it wrote. An incremental build starts from the files whose own text moved and walks the importer graph outwards.

It does not walk the whole importer closure. A file's importers can only observe that file through its declaration output, so sloptor emits the `.d.ts` for each wave of the walk with its own emitter — the same one that writes them, off the untransformed program — compares it against the hash the previous build recorded for that same file, and pulls in the importers **only** of the files whose declaration moved. A comment edit, a renamed local, a changed function body — anything that leaves the declaration byte-identical — recompiles that one file and stops.

**This is TypeScript's rule, not rbxtsc's.** It is the shape-signature reasoning `tsc --incremental` and the `BuilderProgram` behind it use to decide what an edit invalidates. rbxtsc has no equivalent and always rebuilds the whole importer closure, so sloptor selects strictly fewer files than rbxtsc for the same edit and writes the same bytes. Anything the rule cannot establish — a file that emits no declaration, a declaration with no recorded hash, a deleted file — propagates to the importers as before, so an incomplete manifest costs a wider rebuild and never a stale one.

A resolved `.json` module is hashed into the manifest as an input even though nothing compiles it: its value never reaches an importer's Luau (that becomes a runtime require of the copied file), but its inferred type does reach the importer's `.d.ts`, so a change to it rebuilds whoever imported it.

The manifest is invalidated wholesale by a salt over the compiler options, the Rojo and include topology, the native Flamework inputs, and each effective transformer plugin's tsconfig entry, resolved package version, and entry-file hash. **Upgrading or editing a transformer therefore forces one full rebuild**, which is the point: a transformer rewrites the output of every file it sees, and nothing else in the manifest would notice.

Package imports discover `default.project.json` layouts, including nested defaults, but ignore other `*.project.json` files unless a selected layout explicitly references them. This deliberately differs from rbxtsc's package resolver: a generated test project in a dependency's cache or examples folder must not redirect ordinary package imports. Normal project resolvers keep their existing discovery rules. Nested defaults retain their existing behavior, including mounts outside their containing directory; such a default can still redirect an import.

Package builds fingerprint their effective package layouts and declaration-to-runtime mappings, including `main` and `exports` targets, and reuse those inputs for emission. `--build --watch` watches package layout inputs through a separate route that invalidates the owning package project without copying dependency assets. The new route ignores unrelated named projects; a main Rojo config that independently mounts those directories can still trigger its existing reload behavior. Single-project `build --watch` still prunes `node_modules`, so dependency-metadata-only edits require another build trigger or a restart. Game/model `main` and `exports` invalidation and the package's own output resolver are unchanged.

**Hazard.** The rule assumes a transformer's output for a file is a function of that file and the types it can reach. A transformer that carries program-wide state — one that scans every source file to build a registry, and emits different code depending on what else it saw — can go stale, because the files it is handed on an incremental rebuild are only the selected ones. `rbxts-transformer-jecs`, `rbxts-transformer-jest`, the React-compiler applier and native Flamework are all per-file and unaffected. Delete the project's `*.rbxtsc.tsbuildinfo` to force a full rebuild for a transformer that is not.

## Concurrency controls

`--checkers <n>` sets the number of type-checker workers per project. The default is 4, matching TypeScript 7. It applies to `sloptor build`, `sloptor check`, and both watch modes. A CLI value overrides each project's `compilerOptions.checkers`; omitting the flag leaves the project's own config in place. If a project sets `compilerOptions.singleThreaded: true`, it still forces one effective checker regardless of the CLI.

`--builders <n>` sets the number of project-reference builders that run concurrently during solution builds (`--build`). The default is 4; `--builders 1` makes the solution build serial. It is only valid with `--build` — passing it without `--build` is a usage error (exit 1). `sloptor check` does not accept `--builders`.

Both flags accept positive integers only. Missing, zero, negative, or non-integer values are usage errors.

The two flags multiply: `--builders 4 --checkers 4` can run up to 16 checker workers at once, plus parsing, emit, and write work. CPU and memory use grow with the product. Find the right balance for the machine — CI runners with limited cores or memory may want smaller values. For large watch builds, `--build --builders 1 --checkers 1` reduces concurrent compiler state at the cost of potential rebuild latency. The default checker and builder counts remain 4 in watch mode.

**Result guarantees.** Varying `--builders` never changes build results: dependencies always build first, and output, diagnostics, and caching stay deterministic. TypeScript 7 notes that in rare cases varying `--checkers` can surface order-dependent results. Teams that need perfectly stable diagnostics across environments may want to pin `--checkers` to a fixed value.

**Real-world limits.** Even with high concurrency, some work stays serialized. External transformer-plugin sidecars run through Node and may bottleneck a project. Projects whose output or include directories overlap are serialized for safety. And the dependency graph itself bounds how many projects can build in parallel — leaf projects run first, and dependents wait.

These flags control checker and builder parallelism. They are separate from the write-worker environment variables below, which only tune disk-write parallelism.

The write-worker controls are:

- `RBXTSC_WRITE_CONCURRENCY` directly overrides output-write workers and takes precedence over sloptor's setting; values are capped at 256.
- `ROTOR_WRITE_WORKERS` is sloptor's own output-write override.
- Without either override, sloptor uses 8 Go output-write workers. Positive fractional overrides are rounded down; invalid values fall through to the next setting or this default.

`UV_THREADPOOL_SIZE` may still affect the Node sidecar's libuv thread pool, but it does not select sloptor's Go output-write worker count.

When `GOGC` is unset, one-shot CLI commands use `GOGC=400`; `build --watch` (including solution builds), `check --watch` use `GOGC=100` before the initial compilation. The lower watch target collects temporary compiler allocations sooner, with a possible throughput cost. When `GOMEMLIMIT` is unset, sloptor uses 75% of effective memory, clamped from 512 MiB to 16 GiB for one-shot commands and to 6 GiB for watch commands. Linux accounts for finite cgroup v1/v2 limits, while macOS and Windows use the host memory reported by the OS. API watch sessions keep the API process's runtime policy.

Explicit `GOGC` and `GOMEMLIMIT` environment values always take precedence, so they can tune the memory/throughput tradeoff for a particular project. `GOMEMLIMIT` is a soft Go runtime budget, not a hard process-memory cap: it can be exceeded, and it excludes Node transformer children and some OS allocations. Lower checker/builder counts can reduce the live compiler state when a tighter budget causes frequent collection. Watch mode does not force periodic garbage collections or OS memory release.
